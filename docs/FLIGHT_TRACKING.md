# Flight tracking (personal branch only)

This is an experimental, personal-only feature that lives on `personal/flight-tracking`, not `main`. In its lightweight form it shows nearby aircraft on the map while you're navigating: an alert above the search box when one crosses close to your live position, or every aircraft in the area once you're near an airport. It also works with no trip planned at all — see "Idle mode" below.

On top of that, the plane button also opens **Flight Tracking Mode** — a dedicated, full-screen aircraft browser built on the same live-position data, styled after FR24-style trackers (rotated/colored/sized icons, dead-reckoning smoothing between polls, tap-for-detail, search, an airport weather/runway panel) — see its own section below. Both share the exact same `/api/flights` poll; Flight Tracking Mode is a richer way to look at the same data, not a separate feature toggle.

## How it works (nav-mode overhead alert)

- The toggle button sits with voice/satellite in the left-hand control stack (plane icon). It's a per-trip preference: switching it on survives a mid-trip reload/resume (e.g. Android reclaiming a backgrounded tab), but a genuinely new trip always starts with it off again, same as voice guidance defaulting fresh each time.
- While actually navigating (source → destination, live GPS), it behaves as described below. While just browsing/planning, see "Idle mode".
- Every 15 seconds (`CONFIG.FLIGHT_POLL_INTERVAL_MS`), the app asks this deployment's own `/api/flights` route for aircraft near your live position.
- **"Crossing above me"** means horizontal ground-track distance — the distance from you to the point on the ground directly below the aircraft, not true 3D distance including altitude. A 3D check would almost never fire for a cruising airliner (they fly 9-12km up, far beyond any sane metre threshold). Altitude is shown in the alert as extra context, not part of the trigger.
- The distance check doesn't just look at where an aircraft is *right now* — it projects the aircraft's reported track/ground-speed forward across the next poll interval and measures against that whole path (`aircraftApproachDistM` in `app.js`). A fast jet can cover several kilometres in one 15-second poll gap, well more than the overhead radius's diameter — checking only the instantaneous position could miss it crossing directly overhead between two samples entirely.
- A stale position report (`seen_pos` older than `CONFIG.FLIGHT_MAX_POSITION_AGE_S`, 30s by default — common for MLAT-derived fixes lagging behind real ADS-B) is excluded outright rather than trusted as current.
- Get within `CONFIG.FLIGHT_NEAR_AIRPORT_RADIUS_M` (8km by default) of a bundled airport and the behavior switches: instead of only alerting on an overhead crossing, every aircraft the query returns gets plotted on the map — useful for watching approach/departure traffic near an airport rather than just the one plane that happens to pass over you.
- Tap an aircraft marker for its full detail (registration, altitude, speed, distance) in the same badge slot — it reverts to the normal overhead-alert summary on its own after `CONFIG.FLIGHT_DETAIL_DISPLAY_MS` (8s by default).
- If `/api/flights` fails several times in a row (`CONFIG.FLIGHT_CHECKIN_FAIL_WARN_THRESHOLD`, 3 by default), a status message says so once per outage — a single dropped request is ordinary network noise and isn't worth interrupting you about.
- A 429 from the active source specifically pauses polling for a while (`CONFIG.FLIGHT_BACKOFF_BASE_MS`, 30s by default, doubling on each further 429 up to `CONFIG.FLIGHT_BACKOFF_MAX_MS`/5 minutes, or whatever the response's own `Retry-After` header says) rather than keep hitting an already-throttled endpoint every 15 seconds — see `applyFlightBackoff` in `app.js`. Resets back to the normal cadence the next time a check-in succeeds. The proxy (`lib/flights-proxy.js`) also holds a 10-second edge cache keyed by a coarse (~2km) grid cell, to absorb duplicate/retried requests for the same area without ever affecting a normal solo 15s poll.
- The proxy tries [airplanes.live](https://airplanes.live) first, automatically falling back to [OpenSky](https://opensky-network.org) whenever that fails or 403s (any non-OK status or a network error) — see "Data source" below for why airplanes.live is first despite currently doing nothing on this deployment. Which source served a given check-in is reported via the response's `x-flight-source` header; app.js logs which one on the very first check-in of a session and on every later transition, plus names the source explicitly on a failure/429 too.

## Idle mode (no trip needed)

Turning the toggle on while you're just browsing the map — not mid-trip — still works: it rides the same idle GPS watch that powers the "you are here" marker (`startIdleLocationShare`) instead of the real navigation GPS watch, starting that watch itself (silently) if it isn't already running. `maybeCheckFlightsIdle` in `app.js` is the idle-mode counterpart to `maybeCheckFlights`, sharing all the same pacing/backoff/failure-warning state — the two can never poll at once, since exactly one of "navigating" or "not navigating" is true at any moment.

Idle mode always plots every aircraft the query returns, using the same wider regional radius (`CONFIG.FLIGHT_REGIONAL_QUERY_RADIUS_NM`) the near-airport view uses while driving — there's no "en route" sliver of sky to prioritize when you're not actually going anywhere, so the useful behavior is just "show me the local air traffic picture," unconditionally, rather than only alerting on an overhead crossing. The overhead badge and per-aircraft tap-for-detail still work exactly the same as while navigating.

## Flight Tracking Mode (dedicated overlay)

Tapping the plane button opens a dedicated full-screen mode on the same map instance — search bar up top, size-class filter chips, FR24-style aircraft icons, tap-for-detail, tap-an-airport-for-weather-and-runways. Tapping it again (or the hardware/gesture back button) closes it.

**If a trip is active when you open it, the trip is suspended, not ended.** GPS tracking, route progress, voice turn announcements, and rerouting all keep running in the background exactly as before — only the turn-by-turn *visual* UI hides while you're browsing. Closing the mode brings turn-by-turn straight back, camera-follow included, right where the trip left off. If no trip is active, closing the mode also turns the underlying poll off entirely (same as the old simple toggle's on/off behavior) — there's no "trip in progress" to keep alerting for.

**Live aircraft rendering**: aircraft render as a rotated dart icon (not the flat circle the nav-mode badge uses), colored by real airline livery when the callsign prefix is recognized (falling back to an altitude gradient — green low, through cyan/blue, to purple at cruise — when it isn't), and sized by aircraft type. Between the 15-second polls, each aircraft's position is dead-reckoned forward from its last known heading and ground speed so it moves continuously on screen rather than jumping once every poll — capped shorter at low altitude (15-30s depending on altitude) so a stale reading never ghosts an icon implausibly far from where it actually is. Aircraft broadcasting an emergency squawk (7500/7600/7700) get a pulsing red ring.

**Tap an aircraft** for a detail card: callsign, type, registration, altitude/speed/heading/squawk, and — fetched in the background, once — its scheduled route, drawn as a great-circle arc on the map (flown leg dim/solid, remaining leg bright/dashed) that visibly grows as the aircraft moves. Registration/type come from the live poll when available (airplanes.live tier, still pending approval — see below) or a one-off lookup otherwise; route comes from a separate one-off lookup. Either can come back "unknown" for an aircraft with no filed route or an unrecognized registration — the rest of the card still works.

**Tap an airport icon** (or find one via search) for its current METAR weather (temperature, wind, visibility, cloud layers, and a VFR/MVFR/IFR/LIFR flight-category badge using the real aviation color convention, not this app's own info/warn/error palette) and a runway diagram — oriented by heading and scaled by length, not a geographically precise layout (the bundled runway data intentionally has no endpoint coordinates, only headings/lengths, to keep the bundle small).

**Search** looks through the bundled airport list (every commercial airport worldwide, not just ones near you) and whatever aircraft the most recent poll actually returned — it's not a global live-aircraft search, since that would mean either running a stateful backend (explicitly out of scope — this whole feature stays stateless) or spending OpenSky's daily anonymous quota on every keystroke. Search for an aircraft that hasn't shown up in a recent poll and it just won't be there yet.

**Size filter** (All / Wide / Narrow / Regional / GA·Heli) is a pure map filter — it doesn't change what's polled, just what's currently drawn — and resets to "All" every time the mode closes, so a filter from a previous session never silently hides traffic the next time you open it.

## Data source

**Live positions** are backed by [airplanes.live](https://airplanes.live) (the default) with [OpenSky Network](https://opensky-network.org) as an automatic fallback — the same service, in the same order, as [aurora](https://github.com/siddharth2798/aurora) (a separate personal project) uses. airplanes.live is a community-run ADS-B aggregator — real aircraft positions reported by volunteers' own receivers, not an official aviation data service. OpenSky is an academic/non-profit network (ETH Zurich-affiliated) used anonymously, no API key or account. This app calls both through its own `/api/flights` proxy (`functions/api/flights.js` + `lib/flights-proxy.js`), same shape as the existing TomTom/Open Charge Map proxies. The proxy exists purely because neither sends a CORS header, so a browser `fetch()` straight from the client couldn't read the response even though the request itself would succeed. OpenSky's own state vectors already carry ground/airborne status and squawk code for free, so the ground-traffic split and emergency-squawk ring work even on OpenSky alone — only registration and aircraft-type come solely from the airplanes.live tier (or a one-off `/api/aircraft-info` lookup, see below).

**airplanes.live currently does nothing on this deployment**, despite being tier 1: it gates access behind a manual approval email (`contact@airplanes.live`, project description + repo link required), confirmed live via a 403 on every request regardless of User-Agent — aurora's own deployment already has this approval, which is presumably why it was aurora's choice of primary source in the first place. Until that same approval lands here, every single check-in falls through to OpenSky, which is what's actually live today (and what's subject to OpenSky's own 400-credit/day anonymous cap — see the caveats below; a 429 you see in the debug log is OpenSky's limit, not airplanes.live's, and it means both tiers were tried and neither had usable data). This app previously chained through adsb.lol → adsb.fi → OpenSky, before either of the current two sources were in the picture; both of those were dropped for intermittent timing out/rate-limiting on this deployment.

**Aircraft detail and airport info** (Flight Tracking Mode only — these never fire on the lightweight nav-mode badge) are backed by two more free, keyless sources, each with its own thin proxy following the exact same shape as `/api/flights`:

- [adsbdb.com](https://www.adsbdb.com) — `/api/flight-route?callsign=` (`lib/flight-route-proxy.js`) resolves a callsign to its scheduled origin/destination airports and airline, cached 24h since a given flight number's route is stable for the life of that scheduled service; `/api/aircraft-info?hex=` (`lib/aircraft-info-proxy.js`) resolves an ICAO24 hex to registration/type/manufacturer, cached 30 days since airframe data essentially never changes. adsbdb is a smaller, less battle-tested community project than OpenSky or airplanes.live — same "no uptime guarantee" caveat applies, and a failed lookup just shows "Route unknown"/omits the field rather than blocking the rest of the panel.
- [aviationweather.gov](https://aviationweather.gov) — `/api/airport-weather?icao=` (`lib/airport-weather-proxy.js`) fetches current METAR and TAF, cached 20 minutes. This is the FAA/NOAA's own production API (the same one behind US aviation EFBs and briefing tools), by far the most production-reliable of the four sources this feature touches — but its geographic coverage still follows real-world METAR station placement, so a small or rarely-surveyed airfield may simply have no current report.

Neither of these two gets a fallback tier the way `/api/flights` does — both only fire on a discrete tap (open a detail panel, open an airport panel), not a continuous poll, so the pressure that justifies a fallback chain for the live-position feed doesn't apply here; protection is the long cache TTLs above plus each panel section degrading independently rather than blocking the rest of the panel.

**Runway data** comes from the same [OurAirports](https://ourairports.com/data/) dataset the bundled airport list does, regenerated by the same one-off `scripts/build-airport-data.mjs` script into `vendor/runways.json` — intentionally headings/lengths only, no endpoint coordinates, to keep the bundle small (~7,500 runways, under 1MB).

**Honest caveats, worth reading before relying on this for anything:**

- **No uptime or coverage guarantee for any of the four sources.** OpenSky's anonymous tier caps out at 400 free credits/day (roughly 1 credit per query at this app's radii). airplanes.live is a goodwill community project, not a commercial service, once its access approval is granted. adsbdb is smaller still. If one source stops working, the fallback (where one exists) quietly stops mattering for it, or the affected panel section just shows "unavailable," rather than breaking the whole feature.
- **OpenSky's coverage skews toward Europe/North America** more than a readsb-family source like airplanes.live — it's an older, more academically-oriented network. Since OpenSky is what's actually answering every check-in on this deployment today (see above), outside Europe/North America expect thinner results until airplanes.live's approval lands and it starts actually contributing.
- **Coverage depends entirely on ground-receiver density near wherever you're driving.** Busy areas with lots of hobbyist receivers (much of Europe/North America) see rich, near-real-time traffic. Areas with sparse receiver coverage may show little or nothing, even directly under a busy flight path. This is inherent to crowd-sourced ADS-B tracking, not a bug to chase.
- **The callsign shown is the ADS-B/ATC callsign** (the `flight` field, from either source), which usually but not always matches the publicly marketed flight number.
- **Aircraft-type and airline names are best-effort lookups** against bundled static reference tables (`vendor/aircraft-types.json`, `vendor/airline-codes.json` — ICAO DOC 8643 and OpenFlights data respectively). An unrecognized code just falls back to showing the raw code/callsign rather than nothing.
- **The bundled airport list** (`vendor/airports.json`, from the public-domain OurAirports dataset) only includes large/medium commercial airports — small airstrips and helipads won't trigger the near-airport regional view, won't appear in search, and won't have a map icon in Flight Tracking Mode.
- **The route arc, aircraft-info lookup, and airport weather/runway panel are all fetched on demand**, not part of the continuous poll — expect a brief "Route unknown"/"Weather unavailable" flash before they resolve (or a lookup that never resolves for an aircraft/airport neither source has data for).

## Why this isn't on `main`

It depends on an unproven, unofficial third-party data source with no SLA — exactly the kind of thing this project's own convention keeps off `main` until it's been used for a while and proven reliable enough to matter for anyone but the one person who asked for it.
