# Kochi Metro + Kochi Water Metro transit routing

Transit mode routes through Kochi Metro (rail), Kochi Water Metro (ferry), and KMRL's own "Metro Connect" feeder buses using real, bundled station/schedule data — no self-hosted service required. This is deliberately Kochi-specific (see `CONFIG.KOCHI_TRANSIT_ENABLED` in `config.js`), not a generic transit backend. Note the general Kochi-area KSRTC/private bus network (city buses, mofussil/interurban buses) is deliberately **not** covered here — a real GTFS feed for it exists (Jungle-Bus/`KochiTransport`, 461 routes), but at that scale it's a genuine multi-route trip-planning problem, not something this app's per-network leg-builder approach fits; only the small set of feeder routes that connect directly to a metro station are in scope.

## Why no OpenTripPlanner 2 (OTP2)

The app's transit mode also supports a generic OTP2 backend (`CONFIG.OTP2_URL`) for anyone self-hosting a real trip planner for their own city. Kochi doesn't need one: Kochi Metro is a single line (~25 stations), and Kochi Water Metro is ~10 jetties with a small, mostly star-shaped set of direct routes. Running a JVM trip planner for a network this size is disproportionate — it needs a built graph (memory/CPU-heavy, a real risk on something like a Raspberry Pi), a systemd service, and periodic rebuilds, for a problem that's genuinely just "nearest station, count the stops, roughly when." `app.js`'s `buildKochiItineraries` does that directly, and reuses this app's own Valhalla-backed walk/drive routing for the first/last mile (walk if the nearest station is close, drive if it's far — the same choice Google Maps offers for park-and-ride). OTP2 is only tried as a fallback, for a different city entirely.

## Where the data comes from

### Kochi Metro (`vendor/kochi-metro.json`, via `scripts/build-kochi-metro-data.mjs`)

Kochi Metro Rail Limited (KMRL) publishes a real, official static GTFS feed — has since 2018, India's first transit agency to do so.

- **Source**: `http://kochimetro.org/opendata/KMRLOpenData.zip`
- **Required attribution**: *"Contains data provided by Kochi Metro Rail Limited"*
- **License**: free for commercial and non-commercial use, provided AS-IS, no endorsement claims. KMRL does **not** guarantee updates or notify of changes.
- **Rerun the build script** whenever KMRL republishes (e.g. once they extend the calendar past its current end date — see the caveat below), and commit the regenerated JSON.
- **Calendar staleness, checked and harmless**: the feed's own `feed_info.txt`/`calendar.txt` currently end 2025-12-31. This script only extracts the *recurring schedule pattern* (station order, coordinates, real per-station trip-time offsets, real trip start times for weekday vs. weekend service) — not literal calendar-date validity — so a stale end date doesn't affect what's bundled. It would matter if you were doing calendar-exact service-day validation (a real OTP2/GTFS consumer would), which this deliberately isn't.
- **Weekday/weekend split is NOT Mon-Fri/Sat-Sun**: KMRL's own `calendar.txt` defines service `WK` (Monday-**Saturday**) and `WE` (**Sunday only**). `planKochiMetroRideLeg` in `app.js` checks specifically for Sunday, not "is it the weekend."
- **Single line, no branches** — confirmed at build time (the script throws if a future KMRL feed ever shows more than one route or more than 2 shapes, since the whole "just slice an ordered array" approach in `app.js` depends on that).

### Kochi Water Metro (`vendor/kochi-water-metro.json`, via `scripts/build-water-metro-data.mjs`)

**No GTFS or open-data feed exists for Water Metro anywhere** — checked KMRL's own open-data page, Transitland, and the independent `KochiTransport` OSM-derived dataset, which explicitly excludes Water Metro. Two real, unofficial sources fill the gap instead:

- **Schedule + route graph**: `https://watermetro.co.in/api/schedule?from=<Station>&to=<Station>` — a real, live, unauthenticated JSON endpoint on their own site (discovered via the site's own "Boat schedule" search feature, not documented anywhere). Returns genuine per-sailing departure/arrival times. The build script probes every ordered pair among the 10 known terminal names and keeps only the pairs that return real sailings — this is how the actual route graph (20 direct routes, as of this writing) was discovered, rather than trusted from the site's own minified JS bundle, which turned out to contain an internally inconsistent route list when inspected.
- **Jetty coordinates**: each terminal's own page (`https://watermetro.co.in/terminal/<slug>`) embeds a real "Get Directions" Google Maps link pointing at the exact jetty. The build script fetches each page, follows that link's redirect, and parses the resolved URL's own coordinate encoding — first-party data from the operator, not a geocoding guess (a plain Nominatim text search for these jetties turns up nothing at all — checked).
- **This is undocumented and unofficial** — not a published feed, could change or disappear without notice. The build script is deliberately gentle (sequential requests with a real delay) and is meant to be rerun occasionally by a human, never polled by the deployed app.
- **Willingdon Island has no live schedule data** despite being a listed terminal — every pair involving it returned an empty schedule when probed (checked directly). It's still in the bundled station list (for display/geocoding), just unreachable by `findKochiWaterMetroPath` until the live API shows otherwise. Rerun the build script periodically to pick this up if/when it changes.
- **Transfers**: the graph is small and mostly star-shaped through `HighCourt` — `findKochiWaterMetroPath` tries a direct route, then every possible single transfer point. This isn't general graph search; it doesn't need to be, at this size.
- **The network is genuinely two disconnected clusters, not a bug**: `Kakkanad`/`Vytilla` only connect to each other, with no boat link (direct or via any transfer) to the `HighCourt`-hub cluster (`Fort Kochi`, `Vypin`, `Mattancherry`, `South Chittoor`, `Cheranalloor`, `Eloor`) — confirmed both by directly probing the live API (`Fort Kochi→Kakkanad` returns `[]`) and structurally in the discovered route graph. `findKochiWaterMetroPath` correctly returns no path for any cross-cluster pair; that's accurately reflecting how the service actually operates today, not something to route around. Today's one real combined Metro+Water-Metro itinerary transfers through Vyttila/Vytilla specifically because it's the only metro-station/jetty pair within `CONFIG.KOCHI_TRANSFER_MAX_M` (`findKochiTransferPoints`, app.js) — not because that pair is named anywhere in the code. A future data refresh that puts some other station/jetty pair within that same distance would be picked up automatically.

### Kochi Metro feeder buses (`vendor/kochi-feeder-bus.json`, hand-authored)

**No GTFS, API, or open-data feed of any kind exists for these** — KMRL's own official GTFS zip (the same one `build-kochi-metro-data.mjs` downloads) contains only the rail line's single route; KMRL's own "Metro Connect" materials describe GTFS-based live bus tracking as still "planned," not shipped. The only place this network is published at all is `https://kochimetro.org/feeder-service-time-table/` — as a handful of timetable **images** (JPG/PNG), not structured data. There's no build script to rerun (nothing programmatic to call); the JSON is transcribed by hand from those images, the same way `vendor/kochi-water-metro.json` was before this — except Water Metro at least had a live JSON endpoint to cross-check against, and this has no equivalent, so staleness here can only ever be caught by periodically re-checking the images by hand.

- **Scope**: only the ~6 routes that run directly to/from a metro station (Aluva, Kalamassery, Thripunithura) are bundled — Aluva↔CIAL Airport, Aluva↔Rajagiri Hospital, Kalamassery↔Medical College, Kalamassery↔CUSAT (via Rajagiri), Kalamassery↔Infopark (via Civil Station and the Kakkanad Water Metro jetty), Thripunithura↔Infopark (not on Sundays).
- **An older "Pavan Doot" Aluva↔CIAL timetable image also exists on the same page**, with different times and no fare shown, no "Metro Connect" branding — deliberately excluded in favor of the current officially-branded, fare-labeled poster, on the assumption it's a superseded/legacy service. Worth a closer look if the bundled Aluva↔CIAL times ever look wrong in practice.
- **Some routes are simplified past what the source images literally show.** The Kalamassery↔Infopark route's timetable interleaves partial-length trips (some starting from Civil Station rather than Kalamassery, some terminating at Water Metro or Infopark Phase I rather than continuing to Phase II) in a way that doesn't cleanly reduce to fixed per-trip arrival times — this is bundled as a departures list plus a rough `durationEstimateS`, not exact per-trip arrivals, unlike the Medical College route (whose table has clean, unambiguous departure/arrival pairs and is bundled exactly that way). The Kalamassery↔CUSAT table's own column ordering wasn't internally chronological in the source image (possibly a labeling issue on KMRL's own poster) — its times are stored as printed, not resolved.
- **Coordinates**: the three metro-station endpoints reuse the exact same coordinates already in `vendor/kochi-metro.json`; the Kakkanad stop reuses `vendor/kochi-water-metro.json`'s jetty coordinate. Every other stop (CIAL Airport, Rajagiri Hospital, Medical College, CUSAT, Civil Station, Infopark Phase I/II) was geocoded via a plain Nominatim search — these are all well-known, unambiguous named places, unlike Water Metro's small unindexed jetty structures, so the same "no page found" problem that pushed Water Metro toward scraping Google Maps links didn't come up here.

## Fares

Shown per-leg in the maneuver list and as a total on each itinerary card/summary, sourced very differently per network — shown when known, silently omitted when not, never guessed:

- **Metro**: real and exact — KMRL's own GTFS includes `fare_attributes.txt`/`fare_rules.txt` (a flat per-station-pair fare table), parsed by `build-kochi-metro-data.mjs` into a `fares` map on `vendor/kochi-metro.json`, keyed by the same station `id`s already used for everything else.
- **Water Metro**: real, from an official Water Metro-branded fare chart (11 listed station-pairs, ₹20–₹60) — happens to cover all ~20 real routes in the bundled data once each pair is applied to both directions. The chart itself states *"Differential rates will apply on holidays, weekends & festival seasons"* — the bundled fare is the standard-day rate, not guaranteed on those days.
- **Feeder bus**: only as printed directly on the source timetable image, route by route — the CIAL Airport (₹80) and Rajagiri Hospital (₹15) routes show one; the Medical College, CUSAT, Infopark, and Thripunithura routes don't show a fare on their own images at all, so those legs simply have no `fareINR`.

An itinerary whose ride legs aren't *all* priced shows its total as "from ₹X" (`fareIsPartial` on the built itinerary/leg) rather than a number that looks precise but understates the real cost — see `buildKochiItineraries`' own comment on `totalFareINR`/`fareIsPartial` for exactly how that's decided.

## Rerunning the build scripts

```
node scripts/build-kochi-metro-data.mjs
node scripts/build-water-metro-data.mjs
```

Both print a summary (station/route counts, any missing coordinates) and overwrite the `vendor/*.json` files directly — review the diff before committing, same as any other data refresh.

## Rendering

Almost no new rendering code, even for the feeder bus — the map layers/`transitLegIcon` already had a dedicated blue `BUS` color and icon (route_type support inherited from the generic OTP2 path, previously dead code for Kochi specifically), and `renderTransitManeuverList` already builds "Board X, ride N stops, alight at Y" text generically off any itinerary-shaped object — `planKochiFeederBusRideLeg`'s output just tags `mode: 'BUS'` and fits that same shape. `CAR` support (park-and-ride legs) and fare display (`formatFareINR`, per-leg and per-itinerary-total) are the only genuinely new bits.

Each ride leg also carries a real `waitS`/`waitsS` (seconds until the next actual departure(s), computed from the bundled schedule — see `planKochiMetroRideLeg`/`planKochiWaterMetroRideLegs`), shown as a "Next departure in N min" line, or "Next departures in N, M, K min" when more than one real departure is left today (`TRANSIT_UPCOMING_DEPARTURES` in `app.js` caps this at 3). Boarding detection (below) only ever uses `waitS`/`departureAtMs` — the first entry — never the full list. These fields simply don't exist on an OTP2 leg, so that rendering path is untouched — no mode check needed, just `leg.waitsS`.

### Multiple itinerary alternatives

`buildKochiItineraries` builds up to ~10 free candidate specs — metro-only (today's default alighting station, plus the 2 next-best within `KOCHI_METRO_ALIGHT_WINDOW` stations by straight-line distance to the destination), ferry-only, metro+water-metro combined through every real transfer point `findKochiTransferPoints` finds, and metro+feeder-bus combined (capped at `KOCHI_MAX_FEEDER_SPECS`, ranked by how close a route's far endpoint actually is to this trip's origin/destination before spending a Valhalla call on it) — then resolves each candidate's walk/drive access legs via Valhalla (deduped across candidates that share an identical leg — see `cachedDriveOrWalkLeg` — so a plan request costs roughly 6-9 real Valhalla round trips, not a naive ~12), ranks the survivors by total duration ascending (ride-leg time is schedule-exact; Valhalla's access-leg time, even without live traffic, is still road-aware and a better time proxy than raw distance), dedupes by ride-leg signature keeping the faster on a collision, drops any survivor that's both slower and at-least-as-expensive as another (Pareto dominance, only when both fares are known), and caps the result to `KOCHI_MAX_ITINERARY_OPTIONS`. The feeder-bus case needs no transfer-point search the way metro+ferry does — every bundled feeder route already has one end at a metro station's own premises (`feederRouteMetroEnd`, purely coordinate-based, same convention as `findKochiTransferPoints`), so the "transfer point" is just that station, or no metro ride at all if it happens to be the rider's own nearest station. The planning sheet shows every surviving option as a card (`renderTransitItineraryOptions`) — a separate, lighter mechanism from the drive-mode alternate-route cards (`state.routeOptions`/`selectRouteOption`), since nothing about that pipeline (traffic overlays, Fastest/Shortest/tolls tags, gray alternate lines) applies to a bundled Kochi itinerary. The row only appears with 2 or more real candidates.

### Stops

Adding one or more stops (the same "Add stop" UI drive/walk mode already has, up to `CONFIG.MAX_STOPS`) plans each consecutive leg of the trip independently via `buildKochiItineraries` — `buildKochiMultiStopItinerary` fires all of them together (`Promise.all`), safely serialized under the hood by the same Valhalla rate limiter every other call already shares, not one slow sequential chain — then concatenates the shortest candidate from each segment into one itinerary. Segments are independent of each other (the metro/ferry networks one segment resolves against don't interact with another's), so picking each one's own shortest option is provably the shortest whole-trip total too — no combinatorial search across segments needed, and no per-segment alternatives row (that would multiply the choices shown by the number of stops for little real benefit). Every leg except the true final one gets the actual stop's name as its own destination label (`buildKochiItineraries`' `toName` param), not a hardcoded "your destination", so the maneuver list reads e.g. "Walk to Edapally" partway through a multi-stop trip rather than something misleading. Live tracking (below) needs no changes at all for this — it already just walks `state.transitItinerary.legs` by index, and a stitched multi-stop itinerary's legs array looks no different from a single-segment one's. OTP2 has no equivalent — its classic REST planner takes only a plain from/to, no intermediate points — so a multi-stop trip Kochi's planner can't produce fails outright with a clear error instead of silently dropping the stops on an OTP2 fallback.

## Live tracking during the ride

Once `buildKochiItineraries` returns an itinerary (tagged `source: 'kochi'` — the OTP2 fallback never carries this, so none of what follows ever applies to it), the "Start" button reappears on the planning sheet, exactly like it does for drive/walk mode. Tapping it calls `startTransitNavigation`, which starts the same GPS watch (`startLocationWatch`) and live puck (`updatePuck`/`followCamera`) drive/walk navigation already uses, but drives its own leg-by-leg state machine — `state.transitLegIndex`, deliberately not `state.currentLegIndex`, which already means something specific to a drive-mode multi-stop trip — instead of reusing `state.route`. `onPositionUpdate` branches to a separate handler, `onTransitPositionUpdate`, the moment `state.transitTracking` is true, so none of this touches normal drive/walk position handling.

- **Walk/drive legs** (`driveOrWalkLeg`) now carry a real Valhalla maneuver list (`leg.maneuvers`, the exact shape `buildRouteState` produces for `state.route` in normal navigation), so the first/last-mile portion of a Kochi trip gets a real turn-by-turn banner (`updateTransitWalkLeg`) — the same `#nav-banner` drive/walk mode uses, not a simplified "X meters to go" readout.
- **Metro ride legs** show "Next stop: X" and a stops-remaining count, computed off `leg.stations` — the ordered station list `planKochiMetroRideLeg` already builds internally for its own distance calculation, now exposed on the leg so `updateTransitRideLeg` can reuse the same cumulative-distance technique against the live traveled-distance. Once boarded, the leg's own entry in `#maneuver-list` also expands into a full per-station list (`renderStationProgress`), styled with the same `.active`/`.done` classes leg-level highlighting already uses, one level deeper — passed stations dulled, the immediate next station highlighted, upcoming ones plain.
- **Water metro ride legs** have no intermediate-stop data at all (see "no shapes.txt" above), so a ferry leg shows a percent-of-distance-covered readout instead of a station count. (Water metro has no per-station progress list either, for the same reason — that per-station rendering only ever applies to a `SUBWAY` leg.)
- **Boarding detection is a heuristic, not certainty.** `updateTransitRideLeg` only considers you "boarded" once you're within `TRANSIT_BOARDING_RADIUS_M` (config.js) of the ride leg's origin station/jetty coordinate AND at/after that leg's real scheduled departure — `leg.departureAtMs`, an absolute clock time computed from `leg.waitS` at the moment the itinerary was *planned* (`planKochiMetroRideLeg`/`planKochiWaterMetroRideLegs`), not whenever you happen to actually reach the platform. Requiring both, not proximity alone, is deliberate: it avoids reading "standing on the platform waiting" as "already riding the train" just because you're near the tracks. It's still just proximity + a static schedule, though — not a real GTFS-realtime vehicle position, so a late train, or genuinely boarding a different (earlier/later) service than the one this itinerary assumed, isn't distinguished either way. A manual "`I'm on the train`"/"`I'm on the boat`" button (`#board-confirm-btn`) also appears the moment you're within `TRANSIT_BOARDING_RADIUS_M` of the origin — deliberately regardless of whether the scheduled departure time has passed yet, fixing a latent gap in the automatic check above: boarding earlier than the assumed schedule could otherwise never be confirmed until that clock time arrived. Tapping it boards immediately; the automatic proximity+time check keeps running unchanged as a fallback for anyone who doesn't tap it.
- **No reroute for a ride leg — you can't reroute a train.** If the live GPS fix drifts more than `TRANSIT_RIDE_DEVIATION_THRESHOLD_M` from the leg's expected geometry for longer than `TRANSIT_RIDE_DEVIATION_DURATION_MS` (both in config.js, deliberately far more generous than the drive/walk deviation thresholds — GPS on a train or boat is routinely noisier than on an open road), the live progress readout for that leg is just silently hidden (`transitRideHidden`) rather than guessed at or errored on, and it reappears automatically once the fix is back in range.
- **Leg transitions and end-of-trip** (`advanceTransitLeg`) are both proximity-based against each leg's own real destination coordinate, with the same consecutive-fix confirmation (`TRANSIT_ARRIVAL_CONFIRM_FIXES`) the drive/walk arrival check itself uses — a single noisy fix near a station/destination isn't enough to end a leg.
- **Known gaps, honestly**: no voice guidance on any transit leg (drive/walk mode's own turn-by-turn speech isn't wired into this — the banner is text-only here); no wrong-direction or "boarded the wrong train" detection; no PiP integration beyond the same `startLocationWatch`/wake-lock plumbing drive/walk mode already gets for free.

Tapping "End" (`endTransitNavigation`) stops tracking without discarding the planned itinerary itself — `state.route`/`state.transitItinerary` are left alone, so tapping "Start" again resumes tracking from the beginning of leg 0, the same way re-tapping drive mode's own Start button would pick up turn-by-turn guidance again from wherever you currently are.
