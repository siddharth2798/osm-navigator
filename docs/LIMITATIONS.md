# Known limitations

- **Ferry-only-access landmarks**: some pedestrianized OSM landmarks (Gateway of India in Mumbai is the confirmed example) have no drivable road access in Valhalla's graph at all except tourist ferry piers — the app warns rather than silently showing an absurd route, but can't route around a gap in the underlying map data.
- **EV charging search is genuinely sparse** in India's current OSM coverage — turn on `OPENCHARGEMAP_ENABLED` (needs a Cloudflare secret, see [Setup](SETUP.md)) for real connector/power/operator/cost/status detail from a dedicated EV charging database instead. Even then, "status" is Open Charge Map's own community-maintained operational flag, not live occupancy — no data source accessible to a personal project has that. Enabling `TOMTOM_FEATURES_ENABLED` (see [Setup](SETUP.md)) also adds a fallback to TomTom's Places Search for any category search Nominatim comes back empty on, which meaningfully helps here.
- **Transit mode**: a self-hosted OTP2 instance (for a city other than Kochi) still covers planning/rendering only, not live GPS-guided navigation — there's no bundled schedule/station data for a generic backend to detect boarding/alighting against. The bundled **Kochi Metro/Water Metro planner** now searches multiple candidates per trip (metro-only, water-metro-only, and genuine combined Metro+Water-Metro through a real transfer point) and shows up to 3 ranked alternatives as cards when more than one is genuinely plausible. A **Kochi-sourced itinerary** also gets live tracking: tapping "Start" (same button drive/walk mode uses) turns on GPS tracking through every leg — a real turn-by-turn banner on the walk/drive first/last-mile legs, a manual "I'm on the train"/"I'm on the boat" button to confirm boarding the moment you're near the platform/jetty (even ahead of the scheduled departure time), and a "next stop"/stops-remaining readout with a full per-station list for a metro ride, or a percent-of-distance readout for a ferry ride (no intermediate-stop data exists for water metro). Automatic boarding detection (for anyone who doesn't tap the button) is still a heuristic — GPS proximity to the platform combined with the real scheduled departure time, not proximity alone or live vehicle position — and there's no reroute/deviation-recovery concept for a ride leg — a fix that drifts too far from the expected leg geometry for too long just silently stops showing progress for that leg. See [docs/KOCHI_TRANSIT.md](KOCHI_TRANSIT.md) for the exact mechanism and its caveats.
- **Kochi Water Metro's network is genuinely two disconnected clusters** — Kakkanad/Vytilla has no boat link (direct or via any transfer) to the HighCourt-hub cluster (Fort Kochi, Vypin, Mattancherry, South Chittoor, Cheranalloor, Eloor), confirmed against the live schedule data, not a bug in the route search. **Willingdon Island** is a listed terminal with no live sailings at all currently. See [docs/KOCHI_TRANSIT.md](KOCHI_TRANSIT.md).
- **Elevation profile** depends on Valhalla's `/height` action being enabled on whichever server you point at. If a self-hosted server's tiles were built without elevation data, the app detects the resulting flat profile and automatically retries that chart against the public server (see [Troubleshooting](TROUBLESHOOTING.md)) — a fallback, not a fix for the self-hosted server itself.
- **Android shell** — built and running on a real device, including working voice guidance and background tracking/guidance with the screen off or the app minimized.
- **Picture-in-Picture mini view** (this branch only, not `main` — an experimental feature not yet promoted): while actively navigating, leaving the app automatically drops into a small floating window showing the next instruction, distance, and ETA, matching Google Maps' own PiP behavior.
- **The idle location marker's compass wedge** needs a real magnetometer — without one (or if permission is denied), it falls back to GPS-derived heading.
- **Elevation-aware walking features** (this branch only, not `main` — experimental, not yet promoted): the walk-mode elevation profile now feeds more than just the static chart. **Voice incline announcements** speak a one-time heads-up for each upcoming sustained climb/descent (`deriveGradeSegments`/`checkInclineAnnouncement` in `app.js`). A **steep-route advisory** warns before you start if a route's overall climb is unusually high, and **elevation-gain badges** on alternate route cards let you pick the flatter option before committing. A **live effort readout** (round button, walk mode only) shows a qualitative Low/Moderate/High score from pace and climb so far — deliberately not calories, since the app has no user-profile concept to source a body weight from. The **end-of-trip summary panel** this feature set also built is currently disabled (commented out in `endNavigation`, not removed).
